# Cairn UI QA

[개발·검증 기준](../../../docs/development-workflow.md)의 디자인 우선순위와 E2E 경계를 읽는다. 관련 화면만 선택하되 전체 사용자 점검을 요청받았으면 아래 전체 여정을 사용한다. 이 Skill은 새로운 작업 범위·운영 쓰기·예약·배포 권한을 만들지 않는다.

## 경험 품질의 기준

2026-10-31 사용자 요청은 적은 글, 큰 핵심 UI, 자연스러운 탐색과 전환을 요구한다. 이전 구성 문서의 뷰포트 안에 모든 내용을 넣기, 내부 스크롤·확대 화면 중심 배치는 이 요구와 충돌하면 적용하지 않는다. 필요한 문서 스크롤과 화면 재구성을 허용한다. 구현 범위를 작은 단위로 나누더라도 전면 개선 요청을 문구·테두리 수정으로 축소하지 않는다.

- 처음 보는 사용자가 현재 화면의 목적, 핵심 결과, 지금 할 수 있는 행동을 별도 설명 없이 찾을 수 있는지 본다. 완료된 화면은 결과 자체로 충분할 수 있다. 다음 단계 버튼의 존재를 합격 조건으로 삼지 않는다.
- 첫 영역에 핵심 결과와 관련 행동의 우선순위가 드러나야 한다. 여러 카드·버튼이 같은 강조로 경쟁하거나 메뉴·반복 제목이 모바일 결과를 밀어내면 재구성한다. 모든 정보를 첫 화면에 억지로 넣지는 않는다.
- 중복 설명과 내부 용어를 먼저 없앤다. 남은 설명은 필요한 입력 옆의 짧은 도움말이나 선택 시 열리는 상세에 둔다. 긴 글을 전부 접기 카드로 바꾸는 것만으로 단순화했다고 판단하지 않는다.
- 문구는 짧고 자연스러운 말로 쓴다. 제목은 내용을, 버튼은 행동을, 도움말은 필요한 이유를 알려준다. 시스템 보고서 같은 명사 나열, 사용자 탓으로 들리는 오류, 과장된 칭찬을 줄인다. 아이콘·선택 피드백·전환으로 설명할 수 있는 관계는 시각적으로 전달하되 의미 있는 이름을 유지한다.
- 통화·기준 시점·실제/가상·부분 결과·저장 효과처럼 판단에 필요한 구분은 가까이 남긴다. 정상 상태에 반복 경고를 붙이지 않고, 부족·지연·실패는 실제 원인과 가능한 해결 행동으로 설명한다.
- Cairn의 paper/ink, 주황 강조와 음수의 파랑을 유지하면서 넉넉한 여백과 읽기 쉬운 글자·터치 영역을 사용한다. 제목·금액·단위·행동 위치는 공통 토큰과 컴포넌트로 맞춘다. 큰 카드 속 작은 글자, 불필요한 중첩 카드, 페이지별 임의 재정의를 확인한다.
- 토스 등 참고 서비스에서는 정보 순서, 짧은 문구, 선택과 결과의 연결을 가져온다. 홍보용 영상·과도한 둥근 카드·스크롤 효과를 금융 작업 화면에 그대로 복제하지 않는다.
- 눌림·선택·상세 열기·계산 완료·값 갱신의 전환이 변화의 위치와 결과를 알려주는지 확인한다. 반복 등장, 금액의 0부터 재생, 긴 대기 효과를 피하고 reduced motion에서도 같은 결과와 행동을 제공한다.

## 맥락에 맞는 행동과 탐색 안내

필수 해결, 선택적 탐색, 완료를 구분한다. 안내는 현재 계좌·선택·자료·작업 상태에 근거해야 하며 참여를 늘리기 위해 거래나 불필요한 설정을 권하지 않는다.

| 상태 | 확인할 안내와 실제 연결 |
| --- | --- |
| 첫 방문·빈 상태 | 지금 가능한 첫 행동 하나를 중심에 둔다. 예: 보유 종목 등록. 체험을 제공하면 실제 기록과 구분한다. 사용할 수 없는 기능을 여러 개 나열하지 않는다. |
| 목표 미설정·자료 부족 | 부족한 항목을 짧게 특정하고 해당 편집 위치로 연결한다. 일부 결과를 볼 수 있으면 그 결과를 먼저 제공하며 불필요하게 전체 화면을 막지 않는다. |
| 조회 실패·지연 | 확인된 원인에 맞는 재시도나 해결 경로를 제공한다. 단순 조회 실패를 보유 재등록으로 안내하지 않는다. |
| 계산·분석 결과 | 결과와 직접 관련된 주 행동을 우선한다. 예: 예상 배분에서 계획 저장. 비교·계산 방식 확인은 보조 행동으로 제공하고 저장과 실제 거래 기록을 혼동시키지 않는다. |
| 저장·등록 완료 | 완료된 대상과 결과를 보여준다. 필요하면 기록 보기·관련 분석 보기로 연결하되 다음 작업을 강제하지 않는다. |
| 조회·탐색 화면 | 선택한 종목·기간·결과와 관련된 상세나 다른 관점을 자연스럽게 발견할 수 있게 한다. 예: 오늘 변동의 종목에서 해당 종목 이력 보기. 관련 목적지가 없으면 안내를 추가하지 않는다. |

- 버튼·링크는 눌렀을 때의 결과를 짧은 동사와 대상으로 설명한다. 모호한 `다음`, `더 알아보기`를 일괄 사용하지 않는다. 화면 전체를 클릭해야만 행동을 발견하거나 hover에만 의존하지 않게 한다.
- 관련 행동은 결과 근처의 행, 선택 요약, 작은 탐색 링크 등 맥락에 맞는 공통 요소로 표현한다. 항상 떠 있는 팝업·말풍선, 반복 온보딩, 화면마다 같은 추천 카드 묶음을 기본값으로 만들지 않는다. 이동과 현재 화면의 값 변경은 구분한다.
- 실제로 눌러 목적지와 복귀까지 확인한다. 지원하는 계좌/scope, 종목, 기간, 미저장 입력, 선택과 스크롤이 이어져야 한다. 취소·뒤로가기·모달 닫기·해결 후 복귀에서 입력이 사라지거나 같은 안내를 맴돌지 않아야 한다.
- 클릭 영역, 키보드 포커스, 접근 가능한 이름과 touch 피드백을 확인한다. 장식 화살표나 애니메이션만으로 이동 가능성을 표현하지 않는다. 불필요한 거래 유도·긴급성·확정 수익 표현을 추가하지 않는다.

## 대상과 환경

- 현재 checkout/HEAD/diff, URL, 계정 범위, locale, viewport, 실제 데이터인지 개발 예제인지 기록한다. 관련 route → query/model → component와 기존 `e2e/` 테스트를 찾아 확인한다.
- 기존 `playwright.config.ts`와 실행할 spec을 먼저 읽는다. `PLAYWRIGHT_BASE_URL`, 상속 DB 환경, 기존 서버 재사용, 인증 state 때문에 실제 서비스에 접근할 수 있다. 개발 preview는 Production 인증 우회가 아니다.
- 브라우저 조작은 사용 가능한 기존 Playwright Skill/CLI 또는 브라우저 도구를 따른다. 기존 테스트를 복제하거나 브라우저 검증을 위해 새 프레임워크를 설치하지 않는다. 운영 사용이 금지된 경우 격리된 개발 preview만 사용한다. 준비 불가면 로컬 코드 검토는 계속하고 브라우저 결과를 미검증으로 남긴다.

## 화면과 동작

1. 실제 영향을 받는 화면을 1440×900, 1366×768, 390×844에서 본다. 좁은 화면/긴 번역 이슈는 320px도 확인한다. 기존 Desktop Chrome/Pixel 7 프로젝트가 이 정확한 크기를 모두 대신한다고 가정하지 않는다. 수정 전후 같은 데이터·선택 상태의 성공 화면을 캡처한다.
2. 위 경험 품질 기준으로 정보 순서·문구·행동의 발견 가능성을 먼저 평가한다. 데스크톱의 주 시각화·핵심 요약·상세 진입점, 모바일의 요약·행동·간결한 목록을 각각 판단한다. 과도한 카드, 잘린/비어 보이는 그래프, 설명의 밀도, 색 대비와 여백을 직접 확인한다. overflow를 숨겨 통과시키지 않는다.
3. 한국어/영어 전환, 계좌/scope 유지, URL 뒤로가기, 선택·hover·pin, 키보드와 touch, reduced motion을 확인한다. 색만으로 부호·상태를 구분하지 않는다. 설명은 처음 쓰는 사람이 입력 → 계산 → 결과/한계를 따라갈 수 있어야 한다.
4. 날짜 picker와 모달에서 배경/취소/Escape, 포커스 containment/복귀, 내부 링크와 스크롤을 실제로 조작한다. fixed 선택 요약/하단 탐색이 데이터·저장·닫기 버튼을 가리지 않는지 본다. Today 모바일은 종목 터치 → 선택 요약 변경 → 요약에서 상세 열기 흐름을 확인한다.
5. 최초 로딩, 내부 이동, 계산 대기/완료/실패, 데이터 없음/부분/지연 상태를 본다. network/console/trace로 반복 요청, 데이터 waterfall, 불필요한 재마운트, 큰 client bundle, 처음부터 내려받는 상세 내용을 조사한다. 속도 수치를 쓰면 기기·빌드·캐시·조건과 측정 근거를 함께 남긴다. 개발 컴파일 지연을 Production 성능으로 단정하지 않는다.
6. 표시값은 같은 계좌·시각·가격/FX/원가 근거의 모델과 대조한다. 현재 평가액, 오늘 변동, 가격 등락률, 순매매, 누적 손익은 같은 지표가 아니다. 장 전/휴장이라고 0을 강제하지 않고 오래된 기준·결측 이유를 확인한다. preview 숫자만으로 실제 금융 로직을 검증했다고 보고하지 않는다.

## 전체 사용자 점검을 요청받은 경우

먼저 실제 라우트와 공통 화면을 기준으로 `화면/진입 경로 · 사용자 목적 · 상태 · viewport · 핵심 행동/선택적 탐색 · 확인 결과`의 범위표를 만든다. 기존 화면과 베타의 공통 기능은 같은 표시·행동 기준으로 확인한다. 대표 화면 하나나 공통 부품 수정만으로 다른 화면까지 완료 처리하지 않는다. 범위표는 현재 코드로 만들며 과거 라우트 수를 고정된 목록으로 쓰지 않는다.

홈의 종목 흐름/연결/변동 근거 → 오늘 변동 → 추가투입/설명/목표비중 → 포트 구조·위험 → 히스토리 → 투자 랩 → 시뮬레이션 → 관리·온보딩·인증을 돌아본다. 기능/계산 점검에 UI·UX·디자인·성능 점검을 더한다. 어느 하나로 기존 점검을 대체하지 않는다.

이력이 없는 첫 사용자와 돌아온 사용자를 구분한다. 투자 랩/시뮬레이션에서 지금 할 수 있는 첫 행동, 결과 이해, 부족한 데이터의 이유와 다음 단계가 명확한지 평가한다. 이미 승인된 4시간 QA에서는 이전 기록을 읽어 중복 생성을 피하고 아래 경우를 회차별로 순환한다. 이 Skill만으로 즉시 거래 실험을 시작하지 않는다.

| 시나리오 | 관찰할 연결 |
| --- | --- |
| 원가 없이 등록 → 나중에 원가 입력 | 평가액은 가능, 알 수 없는 손익은 null; 현재 원가 입력이 과거 손익/매도의 근거를 소급 조작하지 않음 |
| 새 계좌·ETF·개별주식·신규 종목 | 검증된 종목 선택, 계좌 scope/합계, quote 준비/결측 표시 |
| 매수·추가매수·부분매도 | 수량·평균원가·현금·손익, 지원하는 수수료/세금·외화·소수 수량의 정합성 |
| 전량매도 → 보유 목록에서 제외 → 재매수 | 미세 잔량, 보관/lifecycle, 과거 거래·이력 보존과 현재 보유 재등장 |
| 다른 계좌에 같은 종목 | 수량·원가·거래의 계좌 간 분리, 전체 합계 중복 방지 |
| 저장 연속 클릭·실패·재시도·재접속 | 중복 기록/분실 방지, 저장 결과와 cache/UI 갱신 일치 |

쓰기 실험은 기존에 승인된 QA 신원·실험용 계좌를 확인한 후 서비스가 제공하는 등록/거래 기능으로만 한다. 실제 증권사 주문은 실행하지 않는다. 원래 QA 핵심 기록과 사용자 자산은 보존하고 DB에 직접 과거 기록을 꾸미지 않는다. 저장 성공이 불명확하면 먼저 기존 기록을 확인한다. 대상이나 결과를 확인할 수 없으면 해당 쓰기만 중단하고 다른 확인은 계속한다.

각 회차에서 실제 지원 경로를 확인한다. 미지원 거래는 수량 정정·종료·복원으로 대체하지 않고 기능 공백으로 기록한다.

## 결과

문제별 URL/viewport/locale/data mode, 재현 입력, 예상·실제 결과, 근거, 수정 및 재확인을 남긴다. QA 레코드 식별자는 필요한 로컬 기록에만 남기고 공개 산출물에는 개인값·인증 정보를 넣지 않는다. 관련 수정이 허용됐다면 연결된 공통 구성과 영향 화면을 고친 뒤 재현 경로와 복귀까지 확인한다. 작은 구현 단위는 전체 요청의 완료 범위를 줄이는 근거가 아니다. 리뷰만 요청받았으면 발견 사항을 보고한다.

기능 정합성과 경험 품질을 별도로 판정한다. 정상 동작하더라도 핵심 결과·행동이 묻히거나 설명·탐색 구조가 요청대로 개선되지 않았으면 미해결로 남긴다. 전후 비교에서 무엇을 줄이고 어떤 행동을 더 쉽게 찾게 했는지, 실제 이동·복귀와 상태 유지 결과를 기록한다. 로딩·빈 상태·부분 결과·실패·성공 중 확인하지 못한 상태는 명시한다.

스크린샷/안전한 trace는 `output/playwright/<작업명>/`에 둔다. 파일 존재나 HTTP 200만으로 시각 검증 완료를 선언하지 않는다. 실제 확인한 화면과 상태, skipped/미검증/환경 한계를 구분해 보고한다.

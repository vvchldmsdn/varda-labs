# Varda UI QA

[개발·검증 기준](../../../docs/development-workflow.md)의 디자인 우선순위와 E2E 경계를 읽는다. 관련 화면만 선택하되 전체 사용자 점검을 요청받았으면 아래 전체 여정을 사용한다. 이 Skill은 새로운 작업 범위·운영 쓰기·예약·배포 권한을 만들지 않는다.

## 대상과 환경

- 현재 checkout/HEAD/diff, URL, 계정 범위, locale, viewport, 실제 데이터인지 개발 예제인지 기록한다. 관련 route → query/model → component와 기존 `e2e/` 테스트를 찾아 확인한다.
- 기존 `playwright.config.ts`와 실행할 spec을 먼저 읽는다. `PLAYWRIGHT_BASE_URL`, 상속 DB 환경, 기존 서버 재사용, 인증 state 때문에 실제 서비스에 접근할 수 있다. 개발 preview는 Production 인증 우회가 아니다.
- 브라우저 조작은 사용 가능한 기존 Playwright Skill/CLI 또는 브라우저 도구를 따른다. 기존 테스트를 복제하거나 브라우저 검증을 위해 새 프레임워크를 설치하지 않는다. 운영 사용이 금지된 경우 격리된 개발 preview만 사용한다. 준비 불가면 로컬 코드 검토는 계속하고 브라우저 결과를 미검증으로 남긴다.

## 화면과 동작

1. 실제 영향을 받는 화면을 1440×900, 1366×768, 390×844에서 본다. 좁은 화면/긴 번역 이슈는 320px도 확인한다. 기존 Desktop Chrome/Pixel 7 프로젝트가 이 정확한 크기를 모두 대신한다고 가정하지 않는다. 수정 전후 같은 데이터·선택 상태의 성공 화면을 캡처한다.
2. 데스크톱의 주 시각화·핵심 요약·상세 진입점이 한눈에 읽히는지 본다. 모바일은 요약·행동·간결한 목록의 별도 구성을 평가한다. 과도한 카드, 잘린/비어 보이는 그래프, 설명의 밀도, 색 대비와 여백을 직접 판단한다. overflow를 숨겨 통과시키지 않는다.
3. 한국어/영어 전환, 계좌/scope 유지, URL 뒤로가기, 선택·hover·pin, 키보드와 touch, reduced motion을 확인한다. 색만으로 부호·상태를 구분하지 않는다. 설명은 처음 쓰는 사람이 입력 → 계산 → 결과/한계를 따라갈 수 있어야 한다.
4. 날짜 picker와 모달에서 배경/취소/Escape, 포커스 containment/복귀, 내부 링크와 스크롤을 실제로 조작한다. fixed 선택 요약/하단 탐색이 데이터·저장·닫기 버튼을 가리지 않는지 본다. Today 모바일은 종목 터치 → 선택 요약 변경 → 요약에서 상세 열기 흐름을 확인한다.
5. 최초 로딩, 내부 이동, 계산 대기/완료/실패, 데이터 없음/부분/지연 상태를 본다. network/console/trace로 반복 요청, 데이터 waterfall, 불필요한 재마운트, 큰 client bundle, 처음부터 내려받는 상세 내용을 조사한다. 속도 수치를 쓰면 기기·빌드·캐시·조건과 측정 근거를 함께 남긴다. 개발 컴파일 지연을 Production 성능으로 단정하지 않는다.
6. 표시값은 같은 계좌·시각·가격/FX/원가 근거의 모델과 대조한다. 현재 평가액, 오늘 변동, 가격 등락률, 순매매, 누적 손익은 같은 지표가 아니다. 장 전/휴장이라고 0을 강제하지 않고 오래된 기준·결측 이유를 확인한다. preview 숫자만으로 실제 금융 로직을 검증했다고 보고하지 않는다.

## 전체 사용자 점검을 요청받은 경우

홈의 종목 흐름/연결/변동 근거 → 오늘 변동 → 추가투입/설명/목표비중 → 포트 구조·위험 → 히스토리 → 투자 랩 → 시뮬레이션 → 관리·온보딩·인증을 돌아본다. 기능/계산 점검에 UI·UX·디자인·성능 점검을 더한다. 어느 하나로 기존 점검을 대체하지 않는다.

이력이 없는 첫 사용자와 돌아온 사용자를 구분한다. 투자 랩/시뮬레이션에서 지금 할 수 있는 첫 행동, 결과 이해, 부족한 데이터의 이유와 다음 단계가 명확한지 평가한다. 이미 승인된 4시간 QA에서는 이전 기록을 읽어 중복 생성을 피하고 아래 경우를 회차별로 순환한다. 이 Skill만으로 즉시 거래 실험을 시작하지 않는다.

| 시나리오 | 관찰할 연결 |
| --- | --- |
| 원가 없이 등록 → 나중에 원가 입력 | 평가액은 가능, 알 수 없는 손익은 null; 현재 원가 입력이 과거 손익/매도의 근거를 소급 조작하지 않음 |
| 새 계좌·ETF·개별주식·신규 종목 | 검증된 종목 선택, 계좌 scope/합계, quote 준비/결측 표시 |
| 매수·추가매수·부분매도 | 수량·평균원가·현금·손익, 지원하는 수수료/세금·외화·소수 수량의 정합성 |
| 전량매도 → 보유 목록에서 제외 → 재매수 | 미세 잔량, 보관/lifecycle, 과거 거래·이력 보존과 현재 보유 재등장 |
| 다른 계좌에 같은 종목 | 수량·원가·거래의 계좌 간 분리, 전체 합계 중복 방지 |
| 저장 연속 클릭·실패·재시도·재접속 | 중복 기록/분실 방지, 저장 결과와 cache/UI 갱신 일치 |

쓰기 실험은 기존에 승인된 QA 신원·실험용 계좌를 확인한 후 서비스가 제공하는 등록/거래 기능으로만 한다. 실제 증권사 주문은 실행하지 않는다. 원래 QA 핵심 기록과 사용자 자산은 보존하고 DB에 직접 과거 기록을 꾸미지 않는다. 저장 성공이 불명확하면 먼저 기존 기록을 확인한다. 대상이나 결과를 확인할 수 없으면 해당 쓰기만 중단하고 다른 확인은 계속한다.

각 회차에서 실제 지원 경로를 확인한다. 미지원 거래는 수량 정정·종료·복원으로 대체하지 않고 기능 공백으로 기록한다.

## 결과

문제별 URL/viewport/locale/data mode, 재현 입력, 예상·실제 결과, 근거, 수정 및 재확인을 남긴다. QA 레코드 식별자는 필요한 로컬 기록에만 남기고 공개 산출물에는 개인값·인증 정보를 넣지 않는다. 관련 수정이 허용됐다면 작은 범위에서 고친 뒤 재현 경로를 다시 확인한다. 리뷰만 요청받았으면 발견 사항을 보고한다.

스크린샷/안전한 trace는 `output/playwright/<작업명>/`에 둔다. 파일 존재나 HTTP 200만으로 시각 검증 완료를 선언하지 않는다. 실제 확인한 화면과 상태, skipped/미검증/환경 한계를 구분해 보고한다.
